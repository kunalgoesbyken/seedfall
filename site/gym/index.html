seedfall-gym: an RL environment for crash bugs

Fix the storage code, get rewarded by seeds you never see

November 2026 · Kunal Roy Choudhury

CodeTasksBaselinesseedfall

Abstract—Each task hands an agent a small Go system that loses acknowledged writes or breaks consistency when it crashes. The agent edits the code, and the reward is the share of hidden fault seeds the fixed system survives, replayed through seedfall. Because a seed replays byte for byte, anyone can recompute a reward from the submission. Every one of the 42 tasks is validated the same way: the reference fix scores 1.0, the buggy code scores below 0.5, a scripted cheat scores 0, and doing nothing gives exactly the buggy score.

Index Terms—reinforcement learning environments, reward hacking, automated program repair, fault injection, crash consistency.

The task

The agent gets a workspace with the buggy server, a symptom written the way a user would report it, and one tool that matters: run_seeds, which runs up to four visible seeds and returns pass or fail, the reason and the last 20 trace lines. It can't see the hidden seeds, the salt or the guard report. When it submits, the grader builds the workspace for GOOS=wasip1, runs it on 64 hidden seeds and returns the share that pass. Like SWE-bench [1], the reward comes from running the code, not from a judge model.

A typical symptom, for kvlog-torn-tail: "Under repeated crashes and restarts, including crashes in the middle of a disk write, a client that stored keys and was told OK later reads some of them back as NONE." It never names the bug class or the fix.

Keeping the reward honest

An RL reward is only useful if the cheapest way to raise it is to fix the bug [3]. Every grade goes through four guards:

  • Harness restore. The workload, config and go.mod come from a pristine copy. Only the task's editable paths are taken from the agent, and anything else it touched is listed and ignored.
  • Progress floor. The workload emits an event for every acknowledged operation, counted on the client side so the server can't forge them. A server that refuses every write falls under the floor and scores 0.
  • Determinism. The first two seeds run twice and must give the same host-call hash and verdict.
  • Unfinished runs fail. A server that hangs never finishes the workload, and that seed counts as a failure.

A task only ships if it passes all four validation rules:

Where the tasks come from

Tasks 13 to 42 were made the way SWE-smith makes its tasks [2]: take a seedfall example that's correct, then break exactly one durability mechanism by hand. That means a dropped or misdirected fsync, a missing directory fsync, an ignored I/O error, a step in the wrong order or an offset off by one. Four tasks use key-value stores that Claude models wrote from one prompt, so some of the bugs are bugs a model actually made.

17 candidates didn't make it, and the reasons are listed in the README. Some were reward hacks, where deleting an assertion scored 1.0. Others had a crash window of one disk operation, so the buggy code passed nearly every seed, or a Raft library that wasn't deterministic run to run.

The split is 31 train and 11 held-out tasks. Tasks are grouped by system and bug class, and no group straddles the split, so the held-out set tests bugs the agent hasn't trained on.

Baselines

Two episodes per task on 12 tasks, graded on 64 hidden seeds with a secret salt. Everything ran on free tiers except Haiku, which cost $0.076 in total.

Haiku solved all 24 episodes in about five turns each, so with this prompt the set doesn't separate strong agents yet. Haiku also found a stricter fix than my reference on kvlog-no-checksum, which is how I found out the reference solution was wrong. The flash-lite models struggled on the same three tasks: fsyncgate, the missing checksum and a model-written store.

Limits

  • The set is easy for current small models. A vaguer symptom or a smaller run_seeds budget would make it harder.
  • n is small: two episodes per task, one salt. The two Gemini rows are within noise of each other.
  • A grade takes 5 to 77 seconds, mostly go build and the wazero compile.
  • Every system is Go and fits in one process.
