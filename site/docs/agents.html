Using seedfall from AI coding agents

This page is for people who let an AI coding agent, such as Claude Code, Cursor or Codex, do the testing work. seedfall can talk to the agent directly through an MCP server (a standard way for an agent to call tools) and ships skills (step-by-step instructions the agent follows). Use it to let the agent find a bug, shrink it, fix it and prove the fix.

seedfall mcp serves seedfall's core operations over the Model Context Protocol on stdio. An agent such as Claude Code, Cursor or Codex can then sweep seeds, replay a failure and shrink it on its own, then use the exact fault schedule and trace to fix the bug and prove the fix. No API key and no hosted service are involved: the agent you already use does the reasoning.

Setup

Install the binary first. Every integration below runs it:

go install github.com/kunalgoesbyken/seedfall/cmd/seedfall@latest

Skills

The skills follow the Agent Skills format, so any agent that reads SKILL.md files can use them. To install them with the skills CLI:

npx skills add kunalgoesbyken/seedfall

MCP server

Claude Code:

claude mcp add seedfall -- seedfall mcp

Cursor, or any client that reads an mcpServers file:

{
  "mcpServers": {
    "seedfall": { "command": "seedfall", "args": ["mcp"] }
  }
}

Config paths in tool calls are resolved against the server's working directory, which is normally your project root. Every tool that takes config also takes an optional profile and a set list of path=value overrides, the same as -profile and -set on the command line (config.md).

Tools

Tool Arguments Returns
seedfall_init optional dir, config, nodes, workload, dry_run The module's main packages and which become nodes, the packages that block a GOOS=wasip1 build (compile errors and cgo, each with its import chain and the shim that covers it), compat_shims for every dependency compat_overlay would swap, the starter config and its starter profiles, the files written, and the next steps. See onboarding
seedfall_run config, seeds (for example 1-200), optional rotate, check, skip_pinned, until_novelty, batch, timeout First the pinned regressions, stopping at one that fails again. Then seeds passed, the lowest failing seed with its reason, classification, the faults before the failure, the trace tail, a replay command and artifacts_dir (failure artifacts), plus property coverage, seeds_per_second, virtual_seconds_per_wall_second and utilization (reports.md), and, with faults.buggify on, buggify_sites (buggify). With until_novelty, stopped and the exploration growth table (explore.md)
seedfall_explore config, optional seeds, rounds, batch, until_novelty, budget, explore_seed, keep_going, corpus Feedback-guided search: every round with the new signals and functions it added, the stop reason, the corpus size, property coverage, throughput, and the first failure with artifacts_dir and a replay command (explore.md)
seedfall_replay config, seed, optional faults file The same failure view for one seed, or the trace tail if it passes, with a note when a shrunk schedule's shorter duration ended the run before the workload finished. A failure view of a run that recorded operations also names its history_file and, on a linearizability violation, its timeline_file. Every result has the run's determinism_hash and its events from sim.Event or lifecycle.SendEvent
seedfall_logs config, seed, optional faults, node, grep, from, to, net_trace, limit The run's trace lines filtered by node, regular expression and virtual time, each with its node, instance and time, and a node's slog JSON output parsed into fields, plus how many lines matched (timeline.md)
seedfall_trace_search config, seed, pattern, optional faults, context (default 3), node, from, to, net_trace, limit Each line that matches the regular expression (on the given nodes, inside the virtual time window) with context trace lines of every node before and after it, as windows of numbered lines with their virtual time, node and instance, overlapping windows merged, plus how many lines matched (timeline.md)
seedfall_debug config, seed, optional faults, at, net_trace, commands Replays to at, runs each debugger command (where, net, faults, ls, stat, cat, step, until <regex>, to <time>, branch, log, grep) and returns each output and the final state of every node (timeline.md)
seedfall_shrink config, seed, optional faults (a schedule file, for a failure found by seedfall_explore), budget (runs such as 300, or time such as 10m) The original and minimal sizes (faults, duration and, with sim.Budget, workload operations), the runs used, whether the budget ran out, the path of the saved schedule, and the failure view under that schedule with its replay command (shrinking)
seedfall_faults_edit config, seed, optional faults, remove, shift, add, out Edits a fault schedule to test a hypothesis: remove takes positions counting from 1, shift takes {"fault": 2, "by": "-50ms"} (a count such as "+2" for a fault that fires at a disk operation, read, buggify hit, counted call or udp datagram), add takes faults in the schedule format. Starts from faults, else .seedfall/seed-N.faults.json, else the seed's own faults, checks every fault against the config and writes nothing if one is wrong. Returns the numbered schedule, the file written (out, or the file it came from) and the replay command
seedfall_inspect config, seed, optional faults, at, node, path Every node's disk at the failure or at virtual time at: per file the live and durable sizes, the byte ranges a crash would lose, whether its directory entry is durable, the last torn write, and removed entries a crash would bring back. With path, one file's durable content as text or a hex dump (inspect.md)
seedfall_check history, optional model Re-checks a recorded history file against a model: the verdict, each anomaly with its cycle, and on a linearizability violation the HTML timeline file (properties.md)
seedfall_verify config, seed and optional faults, and/or report; optional seeds, check_seeds, mutate, app_mutants Whether the fix holds: each replayed schedule, the fresh sweep with its confidence, the determinism check and the mutants, plus a Markdown proof block for the PR (verify.md)
seedfall_mutate config, optional seeds (default 1-100), only, app, mutants Sweeps the seeds unmutated, then once per mutant (disk, rename, truncate, network and clock guarantees), or with app once per source mutant of the node packages: each mutant's outcome (killed, survived, not exercised or did not build), its location and change for source mutants, the seed and reason that killed it, and how often the operation was weakened
seedfall_pin config, seed, optional faults Pins the seed's schedule (the one seedfall_shrink saved, the given file, or else the seed's own faults) into seedfall-regressions/ as a permanent regression, and returns the file and whether it passes now, with the failure view if not (verify.md)
seedfall_doctor none Checks the Go version, GOOS=wasip1 builds, net_overlay against the installed Go, a writable build cache and working directory, and free memory, returning the seedfall build and each check as ok, warn, fail or skip with a fix (install.md)
seedfall_findings optional report (default .seedfall/report.html), history, status (comma separated: new, ongoing, regressed, resolved, not seen) Reads a triage report from seedfall run -report without running anything, the same as seedfall findings: each finding with the given statuses with its status, failing seeds, rate, classification and example failure with replay and shrink commands, findings not seen this time, unmet properties, and the run history of that config from .seedfall/history.jsonl (reports.md)
seedfall_cause config, seed, optional points, branches The probability of failing from each moment of the run, with the faults between moments, so the agent can see which event made the failure inevitable (cause.md)

Every result is structured JSON, so the agent can read the seed, the faults and the trace directly.

The same operations on the command line

Every tool has a command, so a person can repeat what the agent did and an agent without MCP can shell out:

Tool Command
seedfall_init, seedfall_run, seedfall_explore, seedfall_replay, seedfall_logs, seedfall_debug, seedfall_shrink, seedfall_cause, seedfall_inspect, seedfall_check, seedfall_verify, seedfall_mutate, seedfall_pin seedfall init, run, explore, replay, logs, debug, shrink, cause, inspect, check, verify, mutate, pin
seedfall_trace_search seedfall trace grep -seed N -e re [-context 3]
seedfall_faults_edit seedfall faults -seed N [-remove 2] [-shift 1=-50ms] [-add '{...}'] [-out file]
seedfall_findings seedfall findings [-status new,regressed] [-json]
seedfall_doctor seedfall doctor [-json]

seedfall schema prints the whole surface as JSON: every command with each flag's name, type, default and usage, and every MCP tool with its description and input and output JSON Schemas, plus the prompts and resources. Generate client bindings or check an agent's calls against it:

seedfall schema | jq '.commands[] | select(.command == "seedfall faults") | .flags[].name'
seedfall schema | jq '.mcp_tools[] | select(.name == "seedfall_faults_edit") | .inputSchema'

Onboarding a new module

seedfall init (MCP: seedfall_init) is the first step in a repository that has never run seedfall:

seedfall init -n                     # report only
seedfall init                        # write seedfall.json and seedfall/workload/main.go
seedfall init -node ./cmd/server     # choose the nodes yourself; repeatable
seedfall init -json                  # the same report as JSON

It runs go list twice. The first run uses GOOS=wasip1 -export -deps, so every package is compiled for wasip1, and any package that fails is reported with its compiler error and the import chain from the node that pulls it in. The second uses GOOS=linux CGO_ENABLED=1 and lists the dependencies that contain cgo files. Every main package that imports net becomes a node. net_overlay is turned on unless every node already uses sim.

The scaffolded workload follows the pattern every example shares: write keys, remember which ones were acknowledged, then read each one back after the faults. Its put and get return errors.ErrUnsupported until the agent implements them against the service's API. Until then the sweep fails with the workload got acknowledged writes never true, so an unwired workload can never pass. Existing files are never overwritten.

On a fresh copy of examples/kvlog with its configs removed, seedfall init -node ./server writes a config and a workload. Wiring put and get to kvlog's line protocol takes about twenty lines. The first sweep then fails on seed 1 with acknowledged write lost, and shrink brings it down to the same two faults as the getting started guide.

Skills

The skills/ directory holds four skills. They follow the order of a real adoption, and every command in them runs as written:

Skill Use it to
seedfall-setup Install, run seedfall init, clear the wasip1 blockers, wire the workload and run the first sweep
seedfall-properties Read the storage and replication code, write sim properties for its durability and consistency promises, and grade them with seedfall mutate until every exercised mutant is killed
seedfall-triage Classify, shrink, find the decisive fault with cause, inspect the disk, and confirm the explanation with a replay of an edited schedule
seedfall-fix-and-prove Fix the cause, replay the saved schedule, sweep, run seedfall verify -mutate -md proof.md and paste the proof into the pull request

The seedfall hook command

seedfall hook is a small command that reads a Claude Code hook payload (JSON with cwd and stop_hook_active) from stdin. It does nothing unless SEEDFALL_HOOK_SEEDS is set, for example to 1-20. It is not installed for you; you only get it by pointing your own hook setup at it.

When the variable is set and seedfall.json exists in the payload's cwd (or the file named by SEEDFALL_HOOK_CONFIG), the command replays the pinned regressions, then sweeps those seeds, under the profile named by SEEDFALL_HOOK_PROFILE if it is set. On a failure, or a property that was never reached or never true, it prints the seed with the replay and shrink commands to stderr and exits with code 2. If stop_hook_active is true it exits 0 without running, so it cannot loop.

A verification loop

Ask the agent to treat a seed sweep as the definition of done for storage or replication changes:

  1. Run seedfall_run over a few hundred seeds before changing anything, to record the baseline.
  2. When a seed fails, run seedfall_shrink and read the minimal fault schedule. It usually names the exact window: "crash during disk op #56", then "crash". seedfall_cause shows which of those faults made the failure likely, and seedfall_faults_edit with out plus seedfall_replay tests a guess, such as dropping a fault or moving a crash one disk operation earlier.
  3. Fix the code, then seedfall_replay the saved schedule until it passes.
  4. Run seedfall_verify with the seed and schedule and paste its markdown proof block into the pull request.

Shrunk schedules are small enough that an agent can reason about them step by step. examples/kvlog is a good first exercise: its seedfall.always.json shrinks to two faults.
